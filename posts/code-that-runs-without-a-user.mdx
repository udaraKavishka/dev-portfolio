The stack trace said `'NoneType' object has no attribute 'is_authenticated'`, and it came from the strangest place: a scheduled job that sends automated messages. The job rendered message templates, the template environment ran a context processor that injects a shared UI element into every page, and that processor checked whether the current user had permission to see it. Under a web request there's always a current user object, even for anonymous visitors. Under a cron job there is no request, no session, and the user proxy resolves to None. One attribute access on None, and a background job that had nothing to do with that UI element died.

This is the bug that taught me to ask a question I now ask about all shared code: who else runs this?

Web frameworks make it easy to assume the request context is the only context. Everything you touch during development happens inside a request. Session, current user, request object, locale, all reliably there. Context processors, middleware, and template globals get written against that comfortable assumption. Then the same template, or the same helper, gets pulled into a CLI command, a queue worker, a scheduled task, or a test, and the assumption becomes a crash.

The fix was one guard: check that the user object exists before asking whether it's authenticated. Three tokens of defensive code. But placing the guard well matters more than writing it. The wrong move is sprinkling None-checks everywhere the symptom appears. The right move is fixing the shared component so every consumer, web or not, gets sane behavior: no user means the element is omitted, render the rest normally. Background contexts shouldn't have to know the processor exists.

Testing this class of bug requires deliberately leaving the comfortable context. My test list for the fix included things that would never have occurred to me a month earlier: run each scheduled command and confirm no render errors, confirm a user with the permission still sees the element, confirm one without it doesn't, and confirm rendering succeeds with no session at all. That last case is the one nobody writes by default, because no browser can produce it. Only infrastructure can, and infrastructure doesn't file bug reports until 2am.

What I took away is a habit of reading shared code with a second lens. When I see `current_user`, or a locale lookup, or anything that smells like request state, inside code that templates or helpers share, I now ask how it behaves when the request machinery isn't there. Most of the time someone already thought about it. The times they didn't, you've found a landmine that a future cron job was going to step on. Finding those before they detonate feels like actual engineering, more than the feature work does some weeks.
